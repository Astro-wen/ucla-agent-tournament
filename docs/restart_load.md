# 重启、慢机器、内存：agent 在比赛日的自我保护（v4.2，09-29）

这份说明写的是 v4.2 这组修复：它们不让 agent 变强，只保证在「进程重启、CPU 被抢、内存紧张」时不掉链子，并且出问题时看得见。本地对局（默认 4 只队伍的写法、不重启）与 v4.1.1 逐局相同，验证见 `docs/progress.md` 的 v4.2 节。

名词（每个一句话）：
- **worker**：官方运行时给每场对局开的一个子进程，里面只有一个 agent 实例。
- **重启**：worker 在对局中途死掉，运行时再开一个新 worker 接着打同一局。新 worker 里是一个全新的 agent 实例。
- **记忆**：agent 在前面几步攒下、后面几步要用的东西，比如选秀时看到的对手完整配置、预览时算出的对手首发分布、谁刚上场（决定能不能用 Fake Out）、狼人杀前几天的聊天记录。
- **状态目录**：存放每局记忆的私有文件夹（权限 0700，文件 0600）。
- **安全网（hard_ms）**：search.js 到点就交答案的时间上限。
- **槽位**：整台机器同时允许运行的搜索进程个数，每个搜索进程占 230–340 MB。
- **健康行**：`scripts/run_agent.sh` 每隔一段时间打的一行 `[health] ...`。

## 1. 重启后接着用原来的记忆（intel-4 / robust-1）

以前：worker 重启后，新实例什么都不记得。搜索只能猜对手的道具和招式，重建出的对手常常只有 2–3 只；狼人杀里前几天的发言全丢。

现在：
- 每做完一个决策，agent 把这一局的记忆写进状态目录里的 `<agent id>--<session id>.json`；知道自己的座位时（官方运行时 `python -m agent --tournament --match` 给的座位号 `seat_position`，否则狼人杀的 `your_position`）文件名再加 `--p<座位>`。写法是先写临时文件再改名（原子写），进程在写的中途被杀，旧文件也还在。
- 为什么要带座位：自对弈测试时（每个座位一个进程，同一个 agent、同一局），如果只按 agent 和 session 存，一个座位第一次决策就会读到另一个座位存的记忆（它的聊天配额、待发的话、收到的私信），不重启也会打乱打法（复审实测：12 局里 3 局打法变了）。现在每个座位各存各的，读回时还会核对存档里的座位。
- 新 worker 在这局的第一个决策时读回这个文件，之后每一步都和没重启时完全一样（单元测试逐步核对：答案相同、写出的记忆也相同）。官方正式赛运行时（`python -m agent --tournament`）里，文件名用的是座位授权（grant）里的 agent id 和对局 session id，同一个座位重启后的 worker 拿到的是同一对，所以同样能接上（`test_the_official_runtime_restarting_a_worker_resumes_the_match`，假的官方客户端）。
- 同一个决策被问两次（运行时遇到竞争错误后重问；或者上一个 worker 已经算出答案、还没发出去就死了），答案不变（robust-3）。
- 文件里只有对局信息（卡牌、物种、我方的选择、读到的聊天），没有任何密钥或环境变量。单个文件最大 1 MB（一局 VGC 约 20–40 KB），超过就不写并打一次日志。
- 清理：平台不会通知 agent 对局结束，所以每个新进程第一次用状态目录时，删掉 3 小时没更新的文件，并且最多保留 200 个。只删状态文件自己的文件（名字是 `xxx--yyy.json` 的样子，和写到一半留下的临时文件），所以就算把 `ARENA_STATE_DIR` 误设成 `data/` 这类放别的文件的目录，也不会删掉别的东西。
- 限制：只有在同一台机器、同一个状态目录上重启才能接上。另一台机器上的热备接管时拿不到这些文件。这时狼人杀至少不会超发或重复发言（robust-9：把 `new_messages` 里自己本窗口已经发过的消息计入 5 条上限）。

开关：

| 变量 | 默认 | 作用 |
|---|---|---|
| `ARENA_STATE` | 录像开着（`ARENA_RECORD` 不是 0）就开 | `1` 强制开，`0` 强制关。本地模拟、重放、测试都设了 `ARENA_RECORD=0`，所以默认是关的 |
| `ARENA_STATE_DIR` | `<ARENA_RECORD_DIR 或 logs>/state` | 状态目录。不可写时退到 `/tmp/arena-agent-<uid>/state`，并打一次警告 |

## 2. CPU 慢或被抢时不再陷入「杀进程—重启—超时」循环（deploy-2 / robust-2）

以前：搜索超时就立刻杀掉搜索进程再重启。新进程要在同样拥挤的 CPU 上重新加载模拟器，所以下一步多半「没热好」，再下一步又超时。最多 6 个进程用完后，这一局剩下的回合就彻底不用搜索了。

现在：
- 超时的搜索不杀，让它在后台算完（search.js 本来就会在安全网处停下交答案）。下一个决策先把这个迟到的答案读掉再发新请求。只有欠答案超过 15 秒（或超时时间的 3 倍）才算真的卡死，才会杀掉重启。
- Python 端多等最多 1.5 秒（`ARENA_SEARCH_GRACE_S`），整个决策仍在 10 秒预算内。安全网不变，所以答案和以前一样。
- 请求前如果花了时间等新进程加载，或者等迟到的答案，就把这次的安全网缩到剩下的时间；剩下不到 0.3 秒就不发请求，进程留着给下一步用。
- search.js 的安全网现在在一行的中间也会检查（以前一整行打完才查，慢机器上一行可能要好几秒）。只影响碰到安全网的搜索。
- 退避期间到点后会在后台重启进程，不再等下一个决策去冷启动。
- 同一局里有 2 次搜索超时（加上宽限也没等到答案，只有 CPU 严重过载才会这样），就改成每次只抽 1 遍（工作量减半，搜索进程更快空出来），并打 ERROR；之后连续 5 次都很快，再恢复原来的抽样数。设了 `ARENA_SEARCH_SAMPLES` 时不自动改。被安全网**截断**但按时交了答案的搜索只计数（汇总行的 `cut=`），不触发这个模式：局面很复杂时，正常负载下也会被截断（09-30 重放真实录像时，负载不高也有 2 局因此触发过旧规则），截断说明不了机器慢。
- 每一次因为机器原因退回经典打法都会打 WARNING；最近 10 个对战决策里有 3 个以上这样，就打一行 `ENGINE SEARCH DEGRADED ...`（ERROR）。

## 3. 内存：整台机器的搜索进程上限（deploy-10）

每局宝可梦要多开一个 230–340 MB 的搜索进程。几局同时开时，内存不够会触发 OOM 或频繁换页。

现在：
- 启动搜索进程前，先占一个槽位（`ARENA_LOCK_DIR`，默认 `/tmp` 下的 `arena-search-slots-<uid>/slot-N.lock`，用 flock 实现）。进程结束或 worker 以任何方式退出，槽位自动释放。
- 槽位数按这台机器（或容器）的内存算：`(min(总内存, cgroup 上限) − 768 MB) ÷ 600 MB`，至少 1 个。1 GB→1，2 GB→2，4 GB→5，8 GB→12。
- 另外要求当前可用内存（`MemAvailable` 和 cgroup 余量取小的）至少 500 MB。
- 占不到槽位或内存不够时，这一局用经典打法，并打一行 `ENGINE SEARCH NOT STARTED: ...`（ERROR，每局一次）。之后每 5 秒再试一次，别的对局结束、腾出槽位后就能恢复搜索。
- 狼人杀不占槽位。
- 只管部署的 agent（录像开着，`ARENA_RECORD` 不是 0）。本地模拟、擂台（ladder）、panel、重放和测试都设了 `ARENA_RECORD=0`，它们不占槽位、不查内存：否则本地评测的结果会取决于机器上同时还跑着什么（例如冠军也换成这版代码后，`python -m local.panel` 默认 6 个并行进程 × 双方各 1 个搜索进程 = 12 个，超过 7.5 GB 机器的 11 个槽位，被拒的那一方整个进程的对局都用经典打法）。想在本地也限，就显式设下面的变量。

| 变量 | 默认 | 作用 |
|---|---|---|
| `ARENA_SEARCH_MAX_PROCS` | 按内存算（只对部署的 agent） | 整数：槽位数；`0`：不限。设了就连本地运行也生效 |
| `ARENA_SEARCH_MIN_FREE_MB` | 500（只对部署的 agent） | 新开搜索进程需要的可用内存。设了就连本地运行也生效 |

## 4. 看得见：录像、每局汇总、健康行（deploy-9）

- **录像**（`logs/<session>.jsonl`）每一行多两个字段：
  - `decision`：`path`（policy / fallback / overrun / crash / busy / repaired / unknown-game，后面可能带 +filled / +repaired）、`kind`、`budget`、`ms`；对战回合还有 `battle`（search = 用了搜索的答案，classic = 经典打法）；重启接上的还有 `resumed`。
  - `search`：这一步搜索的结果：`used`、没用上的原因 `why`、`ms`、`rows`、`cols`、`samples`、`cut`、`lite`。
- **每局汇总**：worker 退出时打一行 `[match-summary] session=… game=… decisions=… battle=… search=search used=… classic=…（原因 x 次数）degraded=… cut=… search_ms p50=… max=… fallbacks=… overruns=… repairs=… resumed=… engine[starts timeouts late busy hung denied slot] calc[…]`。`ARENA_SUMMARY=0` 关闭。进程被 SIGKILL 时打不出来，但健康行的数据每一步都会更新。
- **健康行**的 `search=` 不再只看文件在不在：
  - `ok(used=38/40)`：最近 30 分钟里所有对局的双打回合，≥80% 用上了搜索的答案；
  - `DEGRADED(used=3/20,no_answer=10,not_warm=7,lite=1)`：低于 80%，后面是机器原因的计数；
  - `idle(probe=1.9s)`：最近 30 分钟没有对战，就真跑一次搜索（新开进程、加载模拟器、回答 `data/search_probe.json` 里一个真实的对战决策），最多每 15 分钟一次；`SLOW(probe=4.2s)` 表示超过 2.5 秒；`FAILED(...)` 表示没答出来；
  - `classic(ARENA_BATTLE)`：设了经典打法。
  - 手动查看：`python -m agent.health`。

## 5. 顺带修的输入健壮性

- robust-4：合法动作列表里，双打模板前面多一个动作（比如认输）时，以前会发出一个没有任何选择的 `{"type": "doubles_turn"}`。现在按类型找模板，兜底也不会选认输。
- robust-7：`game_type` 换了大小写或写法（`Pokemon_VGC_Doubles_Draft`、`pokemon`、缺失）时，以前整局都走安全动作；现在按名字或状态的形状认出是宝可梦 / 狼人杀。只写 `pokemon` 时按比赛用的 VGC 双打选秀处理，单打对战状态除外。
- robust-10：卡池里某张卡 `"moves": null` 不再让整个选秀决策崩溃。
- robust-5 的防御：同一个实例被交给另一局时（SDK 不会这样做），先打上一局的汇总，再用全新的记忆开始。

## 6. 要报给上游（主办方 SDK）的

- 运行时不通知 agent 对局结束（没有结束回调），所以每局汇总只能在 worker 退出时打，状态文件只能按时间清理。
- README 写的是重连后 "Nothing is saved locally"，重启后的新实例丢记忆是设计如此；我们在自己的代码里补上了，但另一台机器的热备接管仍会丢。
