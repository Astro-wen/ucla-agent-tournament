# 王者荣耀：公开来源核验与策略边界（2026-10-16）

**结论先行：平台的 5v5 接口已经有公开文档；腾讯公开的 1v1 / 3v3
代码不能直接当成这个平台的 5v5 引擎。** 尤其不要把 `button_7` 一律当治疗，
也不要把示例里的 `9000` 当成所有英雄的攻击距离。

本文只记录能定位的公开来源、来源明确支持的事实，以及**单独标出的待验证建议**。
没有访问私有 Agent_ACP、账号、密钥、真实对局或付费模型；没有运行游戏引擎。
没有取得可验证本策略强度的真实 5v5 战绩。

## 1. 来源与证据等级

- **P：平台合同**，用于判断本比赛的状态和动作是否合法。
- **T：腾讯公开代码 / 官方文档**，能确认对应版本和模式的机制，不保证平台沿用。
- **R：腾讯作者的研究论文**，能确认论文所述实验，不证明其引擎现在公开可运行。
- **H：策略假设**，从前述资料提出的工程建议，不是已测胜率或已确认机制。

## 2. 小兵、防御塔保护：确认了什么

**腾讯一般介绍（T5）**：小兵由游戏逻辑控制，定期沿预定路线行进、自动攻击敌方单位；
塔攻击范围内敌人；要先摧毁防御塔才能伤害基地水晶。
这不是对平台地图中具体哪座塔、哪条路、保护解除条件的完整说明。

**长平 3v3 特定数值（T4，不能直接搬到 5v5）：**

- 前锋塔、基地塔、水晶有顺序要求；说明页写水晶有 90% 减伤。
- 塔在前 2 分钟抵挡英雄的 80 点普攻伤害；无小兵时有 55% 减伤。
- 没有英雄伤害塔下守方英雄时，先攻击最早进入范围的单位；该单位死亡后，
  优先小兵、召唤物、英雄，同优先级取最近者。
- 攻击塔下守方英雄会让塔锁定先造成伤害的敌方英雄，直到其离开范围或死亡。
- 建筑连续攻击会叠加伤害。故“我方还有小兵”并不等于“英雄可以安全打塔下敌人”。
- 该文档写小兵 12 秒开始、每 24 秒刷新，4 分钟后兵种变化，基地塔毁后出现超级兵。
  这些是 **3v3 文档值**，不是本比赛 5v5 的已确认时间表。

**本平台未知（P1 的边界）：** summary 只承诺英雄与建筑，没有承诺兵线 / 野怪列表，
也没有公布塔的射程、无兵减伤、早期保护、攻击转移、塔伤叠加和穿塔顺序。
“没有兵线字段”不等于“引擎没有小兵”；也不能靠开局经过 12 秒就虚构附近有友军小兵。

**H：建议**：看当前合法目标、建筑 HP 是否实际下降、自身 HP 是否快速下降，
避免无条件冲塔。若不能观察小兵，不实现依赖小兵数量 / 刷新时钟的精确波次打法。
若宏标签明确正在打建筑，优先评估普攻而非机械循环技能；
T7 的示例也对建筑偏好普攻，但**不因此声称所有英雄技能都不能作用于塔**。

## 3. 自动购买装备 / 自动升级技能

**已确认：**

- T5 说明金币购买装备、最多六件，经验支持技能升级。这是游戏机制，不是自动操作开关。
- R1 §5 Validation 明确说其 1v1 实验保持双方的**装备购买顺序和技能升级顺序相同**，
  以集中研究战术。说明研究环境可以预先安排这些决策；不说明本平台怎么配置。
- T2 / T3 的动作按钮表没有“买装备”或“加技能点”；
  `Equipment Skill` 是**使用装备主动技能**，不是购买装备。
- P1 没有列出购买或升级命令，也没有说明自动装备 / 自动升级是否开启。

**不能确认：** 本场 5v5 是否自动购买、何时购买、默认出装、技能加点顺序、
能否覆盖这些配置。不能把“没有购买按钮”推导为“已自动购买最优装备”，
也不能推导为“不买装备、永远一级技能”。

**H：建议**：目前不要发送猜测的 shop / level-up 动作，不依赖某英雄已学会某技能。
以每帧实际提供的技能宏为可用性依据。需要主办方公开说明或经授权的合法观测
才能进一步验证自动化；单看 `money` / `level` 不能完整证明购买与加点行为。

## 4. 原始按钮：两份腾讯实现已经不同

下表是 **T2（1v1）和 T3（3v3）的事实**，不是平台 5v5 映射：

| 按钮值 | 腾讯 1v1 | 腾讯 3v3 |
|---|---|---|
| 0 / 1 | 两个无动作项 | 两个无动作项 |
| 2 | 移动 | 移动 |
| 3 | 普攻 | 普攻 |
| 4 / 5 / 6 | 技能 1 / 2 / 3 | 技能 1 / 2 / 3 |
| **7** | **治疗** | **技能 4** |
| 8 | 召唤师技能 | 召唤师技能 |
| 9 | 回城 | 回城 |
| **10** | **技能 4** | **装备主动技能** |
| **11** | **装备主动技能** | **治疗** |
| 12 | 无该项 | 友方赋予的技能 |

平台 P2 明确 `button_0` 无动作，P1 的移动示例使用 `which_button: 2`。
其余完整编号表未公开。**尤其禁止未经平台证据就发送 `button_7` 当治疗。**
即使数值恰好在当前合法列表内，也只保证可提交，不保证想要的治疗语义。

T2 的动作是六部分 `[button, move_x, move_z, kill_x, kill_z, target]`，
维度 `[12,16,16,16,16,8]`；T3 的 3v3 是按钮、单一移动方向、
技能 x/z 偏移、目标，方向有 25 档。不能只因为都有 `which_button`
就认为两者的剩余字段兼容。

**H：建议**：已知宏优先；原始动作只有在所需字段及语义都明确时用于战术。
兜底必须从本英雄当前 `legal_*` 集合填值，不复制论文 / 示例的固定坐标或目标编号。
P1 规定原始动作会清掉常驻命令，因此一次治疗 / 回城尝试后的持续行为也必须重评。

## 5. 目标选择与可见性

- **P1** 的宏是“最近目标”，没有任意指定敌人、统一集火对象或指定路线的宏参数。
  五个英雄都发 `macro_attack`，不等于五人一定攻击同一人。
  宏具体包含哪些目标类型、同距离如何排序，公开指南没有完整定义。
- **T3** 的 3v3 目标槽位是：0 无目标，1–3 敌方英雄，4–6 友方英雄，
  7 自己，8–27 野怪，28–37 敌方小兵，38 敌塔。
  英雄映射代码按 `config_id` 排序（L135–177），不是按平台 seat 排序。
- **T6** 的 1v1 目标表只有无目标、自己、对手、4 个小兵、最近塔。
  T2 的目标合法掩码还依赖所选按钮（L130–163）。
  因此不能把一个 `legal_target` 数字直接解释为 runtime id 或 seat。
- T4 文档说目标表包含最近十个小兵；T7 的 3v3 示例又按 `runtime_id`
  排序取小兵（L348–354）。这种文档 / 示例差异更说明不要倒推平台目标映射。
- **P1** 明确敌人在迷雾里 `visible: false`，不带位置。
  R1 Appendix D 对训练原始状态提到可能提供隐藏单位信息，并要求执行策略时屏蔽。
  论文训练接口不授权参赛策略使用未见状态。

**H：建议**：只用本队当前合法 summary 里明确可见的敌人做局部人数 / 危险判断；
隐藏不等于死亡，没见到敌人也不等于安全。优先相信当前合法动作，
不要自行创造“这个编号应该是敌方水晶”的目标映射。

## 6. 治疗、回城、复活

**已确认的不同层次：**

- P1 的 `macro_retreat` 只是 **walk home**；不是瞬间传送，不是自动回血的承诺。
  `my_hero` 包含 `hp`、`max_hp`、`revive_time`，但没有规定复活计时单位 / 公式。
- T6 的 1v1 `Recall` 是引导数秒、未受打断才回泉水。
- R2 §8.4 的历史 5v5 动作表说 `Return home (Recall)` 需要持续执行；
  `Restore` 在 10 秒内持续恢复、可被打断。**这是 2020 研究版本，不是平台时序保证。**
- T4 的 3v3 在塔后有回血包：60 秒后出现，使用后 60 秒刷新，塔毁后不再刷新。
  不据此假设平台 summary 含回血包或可以通过 `macro_retreat` 拾取。
- T7 的示例明确死亡单位可能暂留在状态列表里，先检查 `hp > 0`。
  仅有坐标 / runtime id 不能证明一个单位仍活着。

**H：建议**：用观测到的生命值变化确认恢复；使用不同撤退 / 返回阈值
（“滞回”，即撤退后多恢复一些再出门）减少来回走。
同时审计“到家却没回血”时的无限撤退：不能无限期假设泉水必然把血补到某个门槛。
`revive_time` 的变化可辅助辨认死亡，但不要猜其单位后自行倒计时复活；
重新看 HP 与合法动作。缺少技能宏也不能单独证明死亡。

## 7. 坐标、距离和时间

- P1 使用世界坐标 `x,z`，未给单位换算、地图边界、阵营镜像方式、通路或各英雄射程。
- T7 的 1v1 示例塔坐标 `[19820,19820]`，3v3 示例 `[48020,6020]`；
  1v1 对阵营 2 反转 x/z，3v3 示例只反转 x。都是对应示例的地图约定，
  不可硬编码为平台 5v5 地图。
- T6 的 **1v1 特征表**给 `hero_attack_range` 2800–8000，
  但这不是平台全英雄范围，也没有建立米 / 厘米换算。
- P3 的 `IN_RANGE = 9000` 和 T7 的 3v3 `distance_threshold = 6000`
  都是**策略阈值**，不是塔 / 普攻 / 所有技能的精确射程。
- P1 已明确没有目标在范围内就不提供 `macro_attack`；
  不应仅因为示例的 9000 或另一个固定阈值而否决当前合法普攻。
  技能宏合法不代表能保证命中、伤害最大或适合目标。
- P1 每步 0.2 游戏秒，默认 3000 步，换算为 **600 游戏秒**。
  这不是无条件的 600 秒墙钟时长，尤其锁步要等待动作；实际还受 `time_limit_s`
  / `seconds_left` 限制。应读每场状态，不凭文档默认值假定剩余时间。

## 8. 能否取得真正 5v5 引擎来验证

**本次未取得，也未运行。**

1. T1 的公开仓库树有 `hok1v1` 和 `hok3v3`，没有对应的公开 `hok5v5` 环境目录。
   R1 2022 论文明确排除 3v3 / 5v5；后来 master 新增 3v3，并不自动新增 5v5。
2. R2 确实是腾讯完整 5v5 研究，不是玩具模拟器；但是论文实验和比赛录像
   不是可供我们本地运行、版本匹配的游戏核心。
3. T1 L74–78 要求单独申请 gamecore 与许可。T8 的游戏核心协议不同于 SDK
   的 Apache-2.0。**不能把公开 SDK 等同于随意下载 / 分发游戏引擎的许可。**
4. P1 说平台运行腾讯服务器，但本次研究未接入服务器，也没有读取私有适配器源码。

结论范围是“**所核验来源没有提供已取得、可合法运行且匹配平台的 5v5 验证环境**”，
不是宣称世界上不存在 5v5 引擎。需要主办方提供公开说明、经许可的匹配测试环境
或合法观测资料；不得自行申请账号、寻找私服或绕过许可。

## 9. 可交给策略作者的改进与验证清单（H，不是战绩）

目标是击败合法的 idle / random / rush 控制，方法必须只依赖合法观测和动作；
**没有真实引擎验证，不能承诺胜率或强度提升。**

| 优先级 | 候选改进 | 证据 / 要防的错误 |
|---|---|---|
| 高 | 五英雄都及时下常驻命令，紧急撤退不饿死其他英雄的调度 | P1/P2；只指挥 seat 0 不是完整队伍 |
| 高 | 有当前合法普攻就参与推进 / 战斗，不因固定距离阈值强制放弃 | P1；9000 不是射程事实 |
| 高 | 宏目标为建筑时评估普攻优先；时限将至优先可获得的建筑伤害 | P1 计分先建筑伤害、后击杀；不为追人丢掉无争议推进 |
| 高 | 撤退根据 HP 下降、可见人数和建筑接近程度，恢复用实际 HP 验证 | T4 危险机制提供动机，平台具体数值仍未知；不能无限待在“假定能回血”的位置 |
| 中 | 每次新状态检查常驻技能是否仍合适；技能不可用时改给当前合法普攻 / 推进 | P1 常驻宏会重算，但未规定宏暂不可执行时怎样替代；不要声称它会自动普攻 |
| 中 | 对纯 rush 的应对测试包括可见的塔下危险、死亡后重新分配、冷却期间行动 | 同时测两边阵营，不把 camp 坐标或特定对手名称作为胜利捷径 |
| 禁止猜测 | 用某按钮治疗、选择目标槽位、固定兵线时刻、购买 / 加点、地图捷径 | 缺平台语义或参数，暂不转为战术代码 |

本地对照的最低定义：

- **idle**：各英雄使用当前合法 no-op（或实时已有合法常驻命令后不更新的独立用例）。
- **random**：只从当前合法宏 / 完整合法原始动作中抽样，不给它非法动作制造失败。
- **rush**：当前能合法普攻则攻击，否则合法推进；逐英雄处理。
- 覆盖两阵营、不同座位 / 宏顺序、技能冷却、死亡 / 复活、雾中敌人、塔已毁、
  攻击目标消失、撤退无回血、锁步待行动集合和时限。
- 没有真引擎时，这些只能检验合同遵守、可复现的决策和特定模拟假设；
  玩具伤害模型、脚本 fake-model 和手工状态的胜率必须标为**合成测试结果**，
  不包装成真实 HoK 强度。真正的宏策略验收还需要小兵、塔保护、治疗、装备与加点
  均匹配的合法 5v5 引擎。
